# コードベースの読み取り

init の手順 3 で、リポジトリを読んで、プリセットと公開範囲の当たりを付け、`guidance.md` の案を作る。

## 読むもの

まず全体の様子をつかむ。

- README、CLAUDE.md、`docs/` などのドキュメント
- 依存のファイル（`package.json`、`pyproject.toml`、`pom.xml`、`go.mod`、`Gemfile`、`composer.json`、`*.csproj` など）と、そこから読み取れるフレームワーク
- ディレクトリの構成（サーバーのコード、フロントエンド、インフラの定義、スクリプトがどこにあるか）

そのうえで、次の観点で読む。全部のファイルを読む必要はない。観点ごとに、当たりを付けるのに足りるだけ読む。

| 観点 | 手がかりの例 | 何に使うか |
|---|---|---|
| どんなプロジェクトか | サーバーを起動するコード、静的サイトとして書き出す設定（静的エクスポート、`dist/` を配信するだけ など）、パッケージとして公開する設定（`"private": false`、公開先の設定）、コマンドの入口（`bin`、`main` 関数） | プリセット |
| どこに公開しているか | デプロイの設定（`Dockerfile`、IaC、ホスティングの設定、CI のデプロイ手順）、認証の仕組み（ログイン、SSO、IP 制限、VPN の前提）、ドキュメントに書かれた利用者 | `exposure` |
| 外からの入力 | ファイルのアップロード、画像や文書の変換、外部の URL を取りに行く処理、Webhook の受け口、利用者が書いた HTML や Markdown を表示する処理 | guidance.md |
| 権限と管理の機能 | 管理画面、権限の区別、管理者だけが使う API | guidance.md |
| 使っていない機能 | 依存しているが使っていない大きな機能（例：フレームワークの SSR を使わず静的に書き出している） | guidance.md |
| 開発と CI | CI のきっかけ（`pull_request_target` やフォークからの PR で動くか）、開発用サーバーの設定（ネットワークに開いているか）、ビルドのときに外部からデータを取ってくるか | guidance.md |
| Issue の決まり | `.github/ISSUE_TEMPLATE/`、CONTRIBUTING、ラベルの使い方 | `action_required` |

## guidance.md の案の書き方

- 判定に効く事実だけを、短い箇条書きで書く。プロジェクトの説明を長々と書かない
- 1 項目ごとに、どこから読み取ったかを書く。推測なら推測だとわかるようにする

```markdown
# dependabot-triage への補足

## プロジェクトの事情

- フロントエンドは静的に書き出して配信している。フレームワークの SSR は使っていない（next.config.js の `output: "export"` から）
- 管理画面（/admin）がある。社内ネットワークからしか開けない想定（推測：README に「社内向け」とあるが、制限の設定は見つからなかった）
- 利用者がアップロードした画像を、サーバーで縮小している（src/upload/resize.ts）

## 開発と CI

- CI はフォークからの PR では動かない（.github/workflows/ci.yml のきっかけが `push` と `pull_request` だけ）
```

- 推測の項目は、担当者に確かめてもらう。確かめられたら「（推測：…）」を外し、違っていたら消すか直す
- 読み取れなかった観点は書かない。かわりに、担当者に聞く（init の手順 4）

## 書かないもの

- パスワード、トークン、鍵などの秘密の値。設定ファイルやコードで見つけても写さない
- ホスト名、IP アドレス、社内のシステムの名前など、判定に要らない具体的な値。「社内ネットワークからしか開けない」のように、判定に要る性質だけを書く
