# プリセット

判定の前提をプロジェクトの種類ごとにまとめたもの。`dependabot-triage.yml` の `preset` で 1 つだけ選ぶ。組み合わせたい部分は `guidance.md` に書く。

プリセットは「どんな攻撃が成り立ちやすいか・どの条件が当てはまりやすいか」の説明にとどめる。深刻度を上げ下げする決まりは、check の判定の基準（`skills/check/criteria.md` の「2 段目」）にだけある。プリセットだけを理由に下げない。

| プリセット | 想定するプロジェクト | 判断の前提 |
|---|---|---|
| `web-service` | インターネットに公開している、サーバーのある Web サービス | ネットワーク経由の攻撃が届く。サーバー側の脆弱性を重く見る |
| `internal-service` | 認証の内側や社内ネットワークからだけ使う、サーバーのあるサービス | インターネットからの攻撃は届きにくい（`exposure: internal` として、2 段目の下げる条件に当たりうる）。ただし、社内の利用者から攻撃が届く脆弱性は「不要」にしない（利用者の PC やアカウントが乗っ取られる場合があるため）。認証の回避と権限の昇格は下げない |
| `static-site` | ビルドして静的なファイルを配信するサイト | サーバー側（SSR、サーバーで動く API など）の脆弱性は、多くの場合成り立たない。ブラウザで動くライブラリの脆弱性（XSS など）は重く見る |
| `library` | ほかのプロジェクトに組み込まれるパッケージ | 「自分は使っていない」は、使う側にもあてはまるとは限らない。公開している機能から脆弱なコードに届くかで判断する。依存の脆弱性は使う側に伝わるものとして扱う |
| `cli-tool` | 手元や CI で動かすコマンドやバッチ | 信頼できない入力（外部のファイル、ネットワークからのデータ）を扱うかで判断する |

## プリセットと公開範囲（`exposure`）の組み合わせ

| 組み合わせ | 扱い |
|---|---|
| `internal-service` と `exposure: internet` | 食い違っている。設定の確かめで警告し、どちらかを直すよう案内する |
| `web-service` と `exposure: internal` | 食い違ってはいない。社内向けでもサーバーのあるサービスは `internal-service` のほうが合うので、そちらを勧める |
| そのほか | どの組み合わせでもよい。たとえば `static-site` と `exposure: internal` は、社内向けの静的サイト |

init で選んでもらうときは、表の「想定するプロジェクト」を見せて選ばせる。どれにも当てはまらなければ、いちばん近いものを選び、違う部分を `guidance.md` に書くよう案内する。
